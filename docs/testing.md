# Testing and known limits

[README](../README.md) · [IFC viewer](ifc-viewer.md) · [Revit and Navisworks](revit-and-navisworks.md) · [Convert to IFC](convert.md) · [Asset register](asset-register.md) · [Facility management](facility.md) · [Development](development.md) · [Testing](testing.md)

This page records how bim-os has been tested so far, with which data, and what has not been tested. The project has no automated test suite in the repository yet; the checks below were run by hand and with scripts kept outside the repository (see [CONTRIBUTING.md](../CONTRIBUTING.md#tests)).

## The viewers

Tested in a headless browser (Chromium) against the development and production builds: IFC conversion and display, Fragments export and re-opening, IFC export of selections, multi-model, box selection, measuring, sections, plans, render styles, both themes, every analysis panel, the in-browser Revit reader on three real projects, and the Navisworks page with the built-in sample (selection, groups, search, IFC export, hand-off to the IFC viewer).

## ifcZIP

ifcZIP was tested in the browser and on the command line with 39 test files made with Info-ZIP and Python: Deflate and stored models, ZIP64, data descriptors, archive comments, data in front of and behind the archive, Finder-style folders with resource forks, UTF-8 and legacy file names, wrong file extensions, several models in one archive, and archives that are encrypted, use other compression methods, hold only ifcXML, or were damaged on purpose in ten different ways. Two more exercise ZIP64 for real: a 4.6 GB archive with the model behind the 4 GB mark, which opens and converts, and an entry that unpacks to 4.5 GB, which was unpacked and checked against its checksum in the browser and on the command line (it is repeated filler rather than one real model, so it was not converted). The unpacked IFC was compared byte for byte with the original, and the Fragments output with that of the plain IFC (identical apart from the random model id every conversion gets). Archives written by Revit, Archicad or other BIM tools were not available to test; they are ordinary Deflate archives. Unpacking in the browser relies on `DecompressionStream`, which Chrome and Edge have had since version 103, Firefox since 113 and Safari since 16.4; only Chromium was tested.

## Folders and exports

Folders were tested in the browser and on the command line with two projects. One is made up for the purpose: models as `.ifc`, `.ifczip` and `.frag`, an extract of another model, a copy under another name, an archive with two models, a damaged archive, Finder leftovers, a `node_modules` folder and a Revit file. The other is real: the Etihad Arena models described under [How much a folder can hold](ifc-viewer.md#how-much-a-folder-can-hold), eleven files of which one is an extract of another. Covered between them: what the dialog proposes, picking a folder and dropping one, the order of opening and of the list, models that wait for a large conversion (also tried with three 200 MB models of one size), showing and hiding, a `.frag` next to its IFC (it opens from the `.frag` and exports IFC from the IFC), both exports, and opening what they wrote. With the ten Etihad models loaded, the `.zip` of ten `.frag` files (449 MB) was written in the browser. With five of them loaded, both exports were written and checked: the `.zip` passes a CRC check and holds the very bytes the models were opened from, and the combined file (210 MB) opened again in a fresh tab in about two minutes, with its five project branches in the tree. Opening a combined file took about five times its uncompressed size at the peak (3.0 GB for that one), so the file of all ten, 1.4 GB uncompressed, was not opened in the 6 GB test browser.

A combined file was compared with the models it was made from, item by item, with the engine's own reader instead of the code that wrote it: for the ten Etihad models joined on the command line (1,904,316 items, 3,965,875 attributes, 2,042,785 relations, 1,472,530 geometry samples and 26.8 million points), for the five joined in the browser (736,924 items) and for the made-up project. Categories, GlobalIds, attributes, relations, geometry and placement came out the same as in the sources. Picking a folder relies on `webkitdirectory` and dropping one on `webkitGetAsEntry`, which Chrome, Edge, Firefox and Safari all have; only Chromium was tested.

## Autodesk Platform Services and the assistant

Not tested against the real services, because no credentials were available while building:

- **Autodesk Platform Services.** The upload, translation, download and delete flows were run end to end against a local stand-in written from Autodesk's official Node SDK (same endpoints, payloads and headers), including a 34 MB multi-part upload verified byte for byte. The real service, and the Autodesk viewer streaming a real translated NWD, have not been exercised. Geometry extraction from the Autodesk viewer was tested with the built-in sample, which is in the older SVF format; translated Navisworks files arrive as SVF2.
- **The Claude API.** The assistant's tool loop, error handling and stop were tested with a scripted stand-in for the model. The server route was checked against the real API as far as authentication (a rejected key gives the expected message).

If something in those paths fails with real credentials, the error shown in the panel comes from the service itself and is the place to start.

## Convert to IFC

The Convert page was tested as follows. The writer was run on the Etihad Arena extracts (twelve viewer extracts, 400,000 elements, 1.4 million fragments) and compared with the IFC files built from them earlier with IfcOpenShell: element counts per discipline, instanced and baked shapes and non-uniform placements match exactly; for 400 sampled elements of the HVAC model and 120 of the signage, matched by GlobalId, the class is the same and the bounding boxes agree to within a micrometre; mirrored and plain elements face outward as in the source. The output passes IfcOpenShell's schema validation and its EXPRESS rules, and web-ifc turns every shape into triangles. In the browser (Chromium, production build): bundle import, discipline suggestions, storeys, generation, and the hand-off to the IFC viewer with discipline files opening together and lining up; the PDF route (pdf.js) and an image route, including scale by drawing scale and by measuring, alignment, tracing, editing and the generated walls and slab; and the bookmarklet end to end on a page running the real Autodesk viewer (the built-in sample, served under viewer.autodesk.com in the test browser): panel, hand-shake, sending to the app, conversion, and the *.eapk* download when the viewer was not opened from the app. On the real viewer.autodesk.com share of the Etihad Arena model (Autodesk viewer 7.129), the extractor found the model's 84 source files, its real file name (the page stores it under a generated one), feet and Z up, and read one source file (853 parts, 700 elements with their properties and units) in under a second; all 735 geometry owners in it fall inside the elements the property reader lists, so geometry and properties line up. The cloud routes for Revit and Navisworks reuse the APS client above and share its untested status; a model translated by APS for this app was not run through the extractor.

### Floor plans from DXF and PDF

The DXF reader was checked against ezdxf on the same plan written as R12, 2000, 2004, 2007, 2010, 2013 and 2018, ASCII and binary (R12 and 2018): release, units, layers, blocks, entity counts and texts match. Recognition was checked against the plan's known layout (a 20 × 12 m office: 12 walls of two thicknesses, 8 doors and a double entrance door, 8 windows, 9 named rooms, 3 round columns) on every release, binary, with the doors and windows exploded, with walls as polylines, as MLINEs, with German layer names, with no units (metres, guessed from the doors), with two floors side by side in one model space, and as PDFs at 1:100 and 1:50 with and without PDF layers (pens): every wall, door, window, room name and number, column and the outline are found, with nothing extra. A plan drawn the way Revit exports walls (separate overlapping outlines), with a 45° wall, a curved wall, exploded doors, a sliding door block, window blocks and room outlines with formatted names reads correctly too. The generated IFC passes IfcOpenShell's schema validation; IfcOpenShell cuts the walls by exactly the openings' volume (four 1.5 × 1.2 m windows in a 300 mm wall: 2.16 m³), doors open towards the side the drawing shows, and the app's viewer and web-ifc open it. In the browser (production build): DXF and PDF plans to the editor, layer roles, selection and editing, generation, the IFC and .frag downloads, two floors stacking in the viewer, the message for a DWG without the add-on. Real-world drawings from many offices were not available for testing; drawings with unusual conventions may need their layer roles set by hand.

### Floor plans from pictures

Pictures were tested on generated plans with known answers: random office layouts (10 to 30 m, a corridor with rooms either side, walls of two thicknesses, doors with their swings and a double entrance, windows, columns, room names, numbers and areas, furniture, dimension chains and a written scale) drawn in five styles (solid black walls, walls as two lines, hatched walls, gray walls with black outlines, colour by layer), at 100 to 300 dpi and at 1:100 and 1:50, then as clean pictures, as scans (turned by up to 1.5°, blurred, noisy, JPEG), as a one-bit fax (also as a CCITT G4 TIFF) and as phone photos (perspective, uneven light, JPEG). Each result was scored against the layout: wall centre lines covered (at the right thickness) both ways, doors and windows by position and width, rooms by overlap and by name, columns by position, and the scale against the true one.

| --- | --- | --- | --- | --- | --- |
| 7 clean pictures (all five styles, 100–300 dpi) | 98–100% / 99–100%, thickness within 0.1–5.4 cm | 64 of 68 (6 extra) | 78 of 80, none extra | 66 of 68 (45) | dimensions: within 0.1%; written scale with the resolution: exact |
| 3 scans and a fax | 91–100% / 98–99% | 31 of 36 | 33 of 43 | 19 of 36 | dimensions: within 0.2–1.6%; written scale: exact |

The text reader read the room names, numbers and dimensions on the clean pictures almost completely (lost: a name crossed by a desk outline), the areas mostly (a superscript ² or a decimal point is sometimes missed). In the browser (Chromium, production build): a clean picture, a phone photo (found, straightened, adjusted) and a fax TIFF read end to end; a room deleted and outlined again by clicking in it; the IFC written; the older tracer and back. With the picture changes, the DXF and PDF checks above give the same results as before.

Pictures that are hardest: scans of solid walls with blur, gray walls on noisy scans and photos, where rooms are found for about half of the rooms (*Outline a room* fills the rest with a click each) and doors drawn faint or broken up can be missed. Real scans and photos from practice were not available for testing; generated pictures cannot show every drawing convention.

### DWG drawings

DWG reading through the optional add-on (GNU LibreDWG, libredwg-web 0.9.3) was tested in four ways:

- **Every drawing in LibreDWG's test data** (141 DWG files, from R1.4 to the 2018 format) converted to DXF without a crash or a read error, the slowest in 1.3 s (Node, one process per file).
- **Against DXF from other software.** 55 of those drawings come with a DXF of the same drawing that LibreDWG did not write. The app read the add-on's DXF and the reference DXF alike (release, layers with their colours and on/off state, entity counts, block references with their position, rotation and scale, mirrored ones included, texts and line work) for 42 of the 43 drawings in the 2000 to 2018 formats; in the 43rd, one entity comes back on layer `0` instead of a layer the reference calls `0 @ 1`. Of the three R13 and R14 drawings, one read alike and two lost two anonymous block references each (old-style hatching; the R13 one most of its hatch lines). Of nine drawings older than R13, four read alike and five lost or gained a polyline or a block.
- **Floor plans with known answers.** The test office plan in six variants (doors and windows as blocks, exploded doors, polylines and MTEXT, MLINE walls, German layer names, metres without units) was saved as DWG in the 2000 format with LibreDWG's own `dxf2dwg` and read back through the add-on: every wall, door, window, room with its name and number, column and the outline was found, as from the DXF (70 checks). LibreDWG's DWG writer is experimental, and some files it wrote were broken (checked with LibreDWG's own tools): mirrored blocks needed a one-line fix to its writer, its R14 files had every layer switched off, and in its files of two plans side by side, and of the Revit-style plan, entities after a point were in the file but missing from model space. Those cases were left out; AutoCAD's own R13 and R14 drawings above read with their layers' colours and states, and its mirrored blocks with their scale.
- **In the browser** (Chromium, production build): without the add-on, a DWG gets the message and nothing is requested from `/addons/`; with it, the office plan as DWG (2000 format) was read in 1.5 s with every element found, generated, and its IFC passed IfcOpenShell's validation with the walls cut by the openings' exact volume; the plan with German layer names and a 2018-format drawing saved by AutoCAD read too; a file that is not a DWG and a cut-off DWG got their messages. No console errors.

libredwg-web 0.7.17, 0.8.0, 0.9.0, 0.9.3 and 0.9.4 were run on the same files (0.8.7 to 0.8.9 crash converting to DXF): the 0.9 releases read 47 of the 55 drawings alike, 0.8.0 46 (it lost line work in a 2000-format drawing) and 0.7.17 43. Real DWG floor plans from practice were not available for testing.

### Room types, notes and the on-device assistant

**Rules.** Room types from names were tested on 112 room names in eight languages and their usual abbreviations (`MTG RM`, `M WC`, `ELEC RM`, `AHU`, `Büro`, `Séjour`, `Majlis`, `مكتب`): all typed as expected. A further 50 harder names (typos, letters misread as digits, Gulf transliterations, other languages) were used to extend the rules, which now read 46 of them (the other 4 name no type), so that set no longer measures them fairly. Notes were tested on ten sets of notes and title blocks in English, French and German (22 values): the rules read all 22, none wrong. Changes in words were checked against a small plan with known answers (which walls are around a room, which door is between two rooms, external and internal walls, renaming, typing, deleting, door types, flipping, undo): 37 checks, all pass.

**The assistant with its real models.** The prompts were tested with the real model weights: the same Qwen3.5 models in llama.cpp's 4-bit GGUF builds, on the CPU, with answers constrained to the same JSON Schemas (as WebLLM's XGrammar does in the browser). The browser runs MLC's 4-bit builds instead, so its answers may differ in places.

| Task | Test set | Rules alone | Qwen3.5 0.8B | Qwen3.5 2B | Qwen3.5 4B |
| --- | --- | --- | --- | --- | --- |
| Room types | 50 names the rules do not know: Dutch, Swedish, Danish, Polish, Czech, Turkish, Malay, Hindi, Arabic, Chinese and Japanese room names, and abbreviations (`BDRM`, `LDRY`, `PWDR`, `WKSTN`) | 0 of 50 | 15 of 50 | 31 of 50 | 46 of 50 |
| Notes | the ten sets above (22 values) | 22 of 22, none wrong | | 22 of 22, none wrong: everything it found that the rules had not was rejected by the checks | |
| Changes in words | 30 requests (English, Arabic, German and French), against the expected changes | | 19 of 30 (7 partly) | 25 of 30; 28 once the editor has matched the rooms named (one more adds a change not asked for, one reads *this is level 2* as a floor level) | |

On two CPU cores the 2B model takes about 15 s to type 13 rooms and 35 s for a change request, the 4B model about 55 s for 13 rooms; speeds in a browser depend on its graphics processor and were not measured. The 2B model is the default, for its download size and memory: the 0.8B one types half as many rooms correctly and misreads more requests (it took *move the kitchen wall 500 mm* for a wall thickness), the 4B one types far more rooms correctly for twice the download (its change requests were not measured). Whatever the model, every change is listed before it is applied, with anything it cannot do said in words, and changes not asked for can be unticked.

**In the browser** (Chromium, production build):

- The plan editor with a DXF plan whose rooms are named in English, Polish, Dutch and Danish, with general notes and a title block beside it: 2 rooms typed from their names and the other 3 by the assistant (a bedroom, a meeting room and an office); the notes gave 8 values, applied to the storey's name, level and height, the door height and the external walls; *walls around the kitchen 150 mm* changed 4 walls, *Undo* put them back; *the door between the kitchen and the corridor is a sliding door* changed that door; *add a staircase* was reported as something the assistant cannot do. The IFC has the room types as ObjectType with *IFCStudio_Space* (type, where it came from, suggested Uniclass SL code), the sliding door's operation type, and the storey's name and level. For this test the page's engine was stood in for by a script handing each task to the same model in Node (llama.cpp), because the test browser's software WebGPU (SwiftShader) cannot run the model.
- Chrome's built-in model, with a stand-in for Chrome's `LanguageModel` that answers through the same model: download progress, one session per task, the JSON Schema as `responseConstraint`.
- WebLLM itself, on SwiftShader's WebGPU: the Qwen3.5 0.8B model downloaded (455 MB, with progress), loaded, kept in the browser's cache and removed from it again. Answering fails on SwiftShader (the graphics device is lost), so answers from WebLLM in a browser were not tested here: that needs a real graphics processor.
- The remembered choice (on, and the model) loads after the page renders, with no hydration warnings; the assistant's code is only loaded in its worker, when it is used.

Not tested: the models on real graphics processors (Mac, Windows), and Chrome's real built-in model (Gemini Nano).

## Materials and textures

Materials and textures were tested on the Autodesk viewer (7.129, the same library viewer.autodesk.com runs) with its built-in sample, with a test picture put on the body material together with a texture matrix (3× scale, 20° turn, offset): the viewer's rendering, the Convert page's preview and the IFC read back independently (texture coordinates, styles and placements parsed from the file with IfcOpenShell, drawn with three.js) show the same squares in the same places from the same camera. Embedded pictures come back byte for byte. Vertex colours (per face and uniform) and a line-only element were tested on synthetic data. The textured, coloured and annotated files pass IfcOpenShell's schema validation and EXPRESS rules, web-ifc turns every shape into triangles, and the app's model viewer opens them (in each surface's average colour). Re-run on eleven of the Etihad Arena extracts, the geometry report (shapes, placements, mirrored, non-uniform, left out) is identical to before; with type objects and material sets the water-services file validates clean. In the browser: preview, picking, *IFC colours*, generation, the ZIP downloads (checked with unzip), and textures arriving through both the viewer link and an *.eapk*. The new extractor was not run on a live viewer.autodesk.com share, so pictures from such a share (which the viewer may load differently) are untested.

## Asset register

The asset register was tested on two made-up models with known answers and on the Etihad Arena extracts. The made-up ones cover rooms with geometry (equipment placed in them by position), rooms named in Navisworks room tabs, an air handler with its diffusers, a chiller and pump on chilled-water systems with an air handler and a fan coil, a board feeding lights through *Panel* and *Circuit*, a stated *Served By*, COBie shared parameters, element lists of systems and classifications in different orders, duplicate tags, placeholders (`n/a`), and dates and durations written in a dozen ways (day-first, `15-Mar-21`, Excel serials, `P5Y`, *Quarterly*, *6-monthly*); every value, room, system, serving link, derived date, PPM job and data issue came out as expected, and the asset ids in both workbooks are the GlobalIds in the IFC. On three Etihad extracts (HVAC, electrical and architecture: 151,021 elements) the register took about 13 s on the command line: 38,345 assets of 1,915 types in 1,582 systems, 957 serving links, rooms only named by the assets (the models have no room geometry), giving a 22 MB COBie workbook and a 6.9 MB asset register. These extracts carry key properties only, so serial numbers, dates, warranty and PPM are empty there; the register reads them when an *All properties* extract has them, as the made-up models show. Both workbooks open in openpyxl and LibreOffice (a LibreOffice round trip keeps every sheet and value). IFC files with asset information pass IfcOpenShell's schema validation and EXPRESS rules (also the 440 MB federated Etihad file with 1,582 systems, 15 zones and 197 room spaces), web-ifc turns every shape into triangles, and IfcOpenShell reads the property sets, systems, zones and room references back. In the browser (Chromium, production build): the card, reading, changing a field's source, both downloads, generation with asset information and the phone layout. Not tested: importing the workbooks into a particular FM platform, and checking them with the COBie QC reporter.

The asset management additions (electrical distribution, technical and fire data, kinds, codes) were tested on a made-up plant with known answers: a transformer feeding a main switchboard, a sub-main board and a distribution board with lights, an emergency light, a socket and a fire alarm panel on it; an isolator fed through a "FED FROM" note; an air handler (airflow in m³/h), a pump (head in metres), a chiller (capacity in TR, refrigerant charge in lb), a fire alarm panel with detectors and a call point on two loops and two zones, a sprinkler, a fire damper, a fire door, a lift, a tank, an extinguisher and a fan that is part of the air handler. The tree, levels and paths, ratings (from "1600 A", "400/230V 3P4W", "50 kA", "IP 54 / IK10"), summed loads, circuits, fire loops and zones, converted values, kinds, codes, parent and parts, Uniclass suggestions and coverage all came out as expected, and the diagrams were checked on that plant and on a wider made-up distribution (2 transformers, 2 main switchboards, 6 sub-main and 24 distribution boards). Every Uniclass code and title in the kind table was checked against the published Pr and Ss tables. On four Etihad extracts (HVAC, electrical, architecture and fire protection: 238,781 elements, 48,145 assets) the register took about 7 s and the workbooks about 19 s on the command line; the kinds were checked against the families found there (which led to rules for CamelCase and Uniclass-coded family names, fused spurs named after what they feed, lift parts and washroom accessories). Those extracts hold key properties only, so ratings and panels are not in them; the distribution there comes from 17 "fed from" notes. The IFC files with the new property sets, systems and classes pass IfcOpenShell's schema validation and EXPRESS rules (the plant, and the 267 MB electrical and 254 MB fire protection files of the Etihad extracts), and web-ifc turns every shape into triangles. In the browser: the field views, codes, the three downloads and generation, in both themes and at phone width.

The register was then checked on the live Etihad Arena share (2026-11-20) with every property of the asset elements: ten of the model's files (HVAC, electrical, fire protection, drainage, water, vertical transport, signage and three architectural files; 343,477 elements) were read in the viewer in 21 s, all properties for the 119,134 elements in asset, room and generic-model categories or without a category, and key properties for the 224,343 pipes, ducts, walls and the like, and joined to the geometry read from the same share earlier. The register (54,681 assets, 2,495 types, 372 boards, 454 circuits, 14,122 fire and life safety items) took 14 s and the three outputs 27 s. That data led to these changes, each now covered by a made-up model with known answers: names with their unit in brackets ("Expected Lifetime (Years)", "Frequency of Maintanance (Months)", with the misspelling) and "Feeder Ref.", "Asset", "Supplied By" and "Installed By" (a new *Installed by* field) are read; zero values ("0.00" cost, "0 VA", "0 A") and COBie's placeholder dates (1900-12-31, and 1999-12-31) count as empty, as does "Please record on commissioning"; only durations count as PPM frequencies (a generator's "Frequency" of 60 Hz does not), only dates as dates and only names as boards (a "DB" of 0.35 does not); Navisworks room tabs are the room's, not the asset's (their Comments and Volume no longer fill asset fields, and they are left out of the asset's properties); a board is named by its panel name; a mark that is a note ("100A TP isolator for … fed from …") names nothing; boards that share a panel name (the model has one placed 18 times) are folded into the best documented one and reported; items wired to data cabinets and security panels are signal links, not part of the power diagram; typographic dashes in board names are read as hyphens; floors whose names read alike ("L03 - VIP Level" and "03 - Main Concourse") get codes of their own; the Asset Properties sheet is written sparsely (4,294 columns) and COBie's Attribute sheet leaves out what the Component and Type rows already say (768,721 rows, under Excel's limit). The workbooks open in openpyxl and LibreOffice.

## Facility management

The facility workspace's core (storage, edits and their reversal, checks, the task library and scheduling, work orders and plans moving on, alarms, search and filters, Brick, QR codes, workspace and change files, merging) was checked with a script of 39 assertions on the demo building and made-up cases.

**IFC as a source.** The IFC file bim-os wrote for the made-up plant used for the asset register (23 assets of every discipline in two rooms) was read back with web-ifc and its register compared with the one built from the original model: the same assets with the same GlobalIds, names, kinds, rooms, floors, categories, parents and values of 26 fields (ratings, flows, capacities, refrigerant, fire data, panels and circuits), the same electrical tree and relations, and the same issue. Reading it back led to leaving out what bim-os itself worked out (codes, relations, its derived systems). The four Etihad Arena IFC files written earlier (architecture 397 MB, mechanical 44 MB, electrical 267 MB, fire protection 254 MB) were read on the command line in 2 to 45 s each, and together into one register of 43,023 assets in 78 s (2 GB of memory); their storeys (49 across the files) became 21 floors before storeys were also merged by name, and a made-up case checks that merge. In the browser (Chromium, production build) the four were read in 77 s and onboarded end to end, including the COBie, register and diagram downloads. Those files carry no room shapes (their rooms are only named), so placing equipment in rooms by geometry was checked with the made-up plant, whose rooms have shapes.

**In the browser** (Chromium, production build, desktop and phone sizes): the welcome page; the demo; Home; the search palette (keyboard, scopes, opening results); the Assets page with filters and facets, editing a field (with the model's value kept), checking an asset on site, and exports; raising work orders from the due list, completing one with a note (its plan moving on); the calendar; labels; the field app opening an asset by its code; exporting the workspace; onboarding from an IFC file through every step; and live data from a real MQTT broker (aedes) over WebSocket with a user name and password: topics discovered and linked to their assets by name, an alarm limit set, the alarm raised by the readings, acknowledged, and shown on the asset. With the service worker active, the field app opened with the network switched off. A second browser profile starting without a workspace checked that each device keeps its own.

**Not tested:** printing labels on a real label printer, scanning a printed label with a phone (the browser's code reader needs a real camera), Safari and Firefox, brokers behind TLS (`wss://`) and the share sheet on real phones.

## Known limits

Other limits worth knowing:

- The importer cannot turn every piece of geometry into a surface. It leaves out what it cannot (its own log calls these "problematic geometry"), and the app counts them instead of passing on a line for each: the conversion message and the model's details give the number, and so does the command line. In the Etihad project three of the ten models had some: 7,896 pieces in the fire-protection model, 191 in the electrical one and 85 in the interiors. Every element in those models still has geometry, so what is missing are parts of elements. A model opened from a `.frag` does not carry the count.
- While several large models load one after another, the browser console can show WebGL warnings ("no buffer is bound to enabled attribute") from the engine's level-of-detail meshes. They come with models that arrive in quick succession, also when several files are picked at once with *Open files*, and did not appear when the same models were opened one at a time with a pause in between. The finished picture was complete in every test.
- Analysis panels index a model the first time they are used. On very large models that takes a while (about a minute at 150,000 elements; quantity take-off, which reads every property set, took about four).
- Storey plans are clipped top-down views; cut faces are not hatched.
- Plan walls meeting at angles other than 90° overlap a little at the corner (walls are rectangles, not mitred). DWG files need the optional DWG add-on (`npm run addon:dwg`); without it, save them as DXF. Through the add-on, R13 and R14 drawings can lose old-style hatching and drawings older than R13 read only in part.
- Pictures: the text reader knows English only (other Latin-script names are read with some errors); stairs, curtain walls and grids are not recognised; on scans and photos doors and rooms are found less often than on clean pictures (see above).
- The ground grid is drawn in the *Fast* render style only.
- The Navisworks viewer is set up for the US, EMEA and AUS regions.
- The facility workspace lives in one browser on one device; devices share it as files, and a workspace file is opened as a whole (change files are merged).
